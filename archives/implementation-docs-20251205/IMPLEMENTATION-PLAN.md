# Cortex Enhancement Implementation Plan

**Date:** 2025-12-04
**Scope:** High-priority improvements from React Grab, Anthropic Harnesses, and Autonomous Coding Quickstart analyses
**Pain Points Addressed:** Task completion accuracy, session continuity, token efficiency, testing gaps

---

## Overview

This plan implements four core improvements to Cortex:

1. **Initializer Master** - New 6th master for task decomposition
2. **Feature List Pattern** - 200+ atomic features per major task
3. **Progress Tracking** - Session continuity mechanism
4. **Test Enforcement** - Validation gates before task completion

---

## Phase 1: Foundation (Core Infrastructure)

### 1.1 Create Initializer Master

**Location:** `coordination/masters/initializer/`

**Components:**
```
coordination/masters/initializer/
├── initializer-master.sh           # Main entry point
├── lib/
│   ├── feature-decomposer.sh      # Task → 200+ features
│   ├── init-script-generator.sh   # Generate worker init.sh
│   └── specification-parser.sh    # Parse task requirements
├── prompts/
│   ├── decomposition-prompt.txt   # Claude prompt for feature generation
│   └── test-generation-prompt.txt # Generate test commands
└── config/
    └── decomposition-policy.json  # Rules for feature granularity
```

**Responsibilities:**
- Read task specifications from Coordinator
- Decompose into 200+ atomic features
- Generate feature list JSON
- Create init.sh scripts for workers
- Hand off to appropriate master (Dev/Security/etc.)

**Integration Point:**
- Coordinator routes complex tasks to Initializer first
- Initializer creates feature list, then routes to execution masters

**Status Values:**
- `failing` - Not yet implemented
- `in_progress` - Worker currently implementing
- `passing` - Tests pass, feature complete
- `blocked` - Waiting on dependencies

### 1.4 Init Script Pattern

**Location:** `coordination/workers/{worker-id}/init.sh`

**Generated by Initializer Master per task:**
```bash
#!/bin/bash
# Auto-generated init script for worker-implementation-001
# Task: task-auth-implementation-001
# Generated: 2025-12-04T10:00:00Z

# Verify working directory
cd /Users/ryandahlberg/Projects/cortex || exit 1

# Load environment
source ./config/load-env.sh

# Install dependencies if needed
if [ ! -d "node_modules" ]; then
  npm install
fi

# Run database migrations
npm run db:migrate

# Verify tests can run
npm test -- --listTests > /dev/null 2>&1
if [ $? -ne 0 ]; then
  echo "ERROR: Test environment not ready"
  exit 1
fi

# Load feature list
export FEATURE_LIST="coordination/feature-lists/task-auth-implementation-001-features.json"

# Load previous progress
if [ -f "coordination/workers/$WORKER_ID/progress/current-session.json" ]; then
  echo "Previous session found, loading context..."
  cat "coordination/workers/$WORKER_ID/progress/current-session.json"
fi

echo "Environment ready. Feature list loaded: $(jq '.total_features' $FEATURE_LIST) features"
```

### 2.2 Development Master Updates

**File:** `coordination/masters/development/development-master.sh`

**Changes:**
1. Check for feature list before spawning workers
2. Select next incomplete feature (highest priority, no blockers)
3. Pass feature-specific context to workers
4. Enforce test validation before marking features complete

**New Spawn Logic:**
```bash
spawn_implementation_worker() {
  local task_id=$1
  local feature_list="coordination/feature-lists/${task_id}-features.json"

  if [ -f "$feature_list" ]; then
    # Get next feature to implement
    next_feature=$(jq -r '.features[] | select(.status=="failing" and (.dependencies | length == 0 or all(.dependencies[] as $d | any(.features[] | select(.feature_id==$d and .status=="passing")))) | .feature_id' "$feature_list" | head -1)

    if [ -z "$next_feature" ]; then
      echo "No available features to implement (all complete or blocked)"
      return 0
    fi

    echo "Spawning worker for feature: $next_feature"
    GOVERNANCE_BYPASS=true ./scripts/spawn-worker.sh \
      --type implementation-worker \
      --task-id "$task_id" \
      --feature-id "$next_feature" \
      --master development-master
  else
    # No feature list, use existing logic
    spawn_worker_old_way "$task_id"
  fi
}
```

### 2.3 All Masters: Test Enforcement

**Files:** All master scripts

**Add validation gate:**
```bash
validate_worker_completion() {
  local worker_id=$1
  local task_id=$2
  local feature_id=$3

  # Check if feature has test command
  local test_cmd=$(jq -r ".features[] | select(.feature_id==\"$feature_id\") | .test_command" \
    "coordination/feature-lists/${task_id}-features.json")

  if [ "$test_cmd" = "null" ] || [ -z "$test_cmd" ]; then
    echo "WARNING: No test command defined for $feature_id"
    return 1
  fi

  # Run the test
  echo "Running validation: $test_cmd"
  eval "$test_cmd"
  local exit_code=$?

  if [ $exit_code -eq 0 ]; then
    echo "Tests passed for $feature_id"
    # Update feature list
    jq ".features |= map(if .feature_id == \"$feature_id\" then .status = \"passing\" | .completed_at = \"$(date -u +%Y-%m-%dT%H:%M:%SZ)\" else . end)" \
      "coordination/feature-lists/${task_id}-features.json" > tmp.$$.json
    mv tmp.$$.json "coordination/feature-lists/${task_id}-features.json"
    return 0
  else
    echo "Tests failed for $feature_id"
    # Keep status as in_progress or failing
    return 1
  fi
}
```

This addresses **task completion accuracy** and **testing gaps**.

### 3.2 Worker Session Management

**File:** `scripts/lib/worker-session.sh` (new)

**Functions:**
```bash
#!/bin/bash

start_worker_session() {
  local worker_id=$1
  local task_id=$2
  local feature_id=$3

  local session_dir="coordination/workers/${worker_id}/progress"
  mkdir -p "$session_dir"

  # Find next session number
  local session_num=$(ls -1 "$session_dir"/session-*-progress.txt 2>/dev/null | wc -l)
  session_num=$((session_num + 1))

  local session_file="${session_dir}/session-$(printf '%03d' $session_num)-progress.txt"

  # Initialize session
  cat > "$session_file" <<EOF
Session: $(printf '%03d' $session_num)
Worker: $worker_id
Started: $(date -u +%Y-%m-%dT%H:%M:%SZ)
Task: $task_id
Feature: $feature_id

=== What Was Done ===
(Session in progress...)
EOF

  # Create current session symlink
  ln -sf "session-$(printf '%03d' $session_num)-progress.txt" "${session_dir}/current-session.txt"

  echo "$session_file"
}

end_worker_session() {
  local worker_id=$1
  local session_file=$2
  local git_commits=$3

  # Update session end time
  sed -i '' "s/Started: \\(.*\\)/Started: \\1\\nEnded: $(date -u +%Y-%m-%dT%H:%M:%SZ)/" "$session_file"

  # Add git commits
  echo "" >> "$session_file"
  echo "=== Git Commits ===" >> "$session_file"
  echo "$git_commits" >> "$session_file"
}

load_previous_session() {
  local worker_id=$1

  local session_dir="coordination/workers/${worker_id}/progress"
  if [ -f "${session_dir}/current-session.txt" ]; then
    cat "${session_dir}/current-session.txt"
  fi
}
```

### 3.3 Worker Completion Criteria

**Update all worker scripts to enforce:**

Before marking task complete, worker must:
1. ✅ Run test command from feature list
2. ✅ Verify test exit code = 0
3. ✅ Commit changes to git
4. ✅ Write session progress file
5. ✅ Update feature list status to "passing"

If any step fails, keep status as "in_progress" and report blocker.

This addresses **task completion accuracy** and **testing gaps**.

### 4.2 Governance Validator Script

**File:** `lib/governance/completion-validator.js` (new)

```javascript
const fs = require('fs');
const { execSync } = require('child_process');

function validateWorkerCompletion(workerId, taskId, featureId) {
  const violations = [];

  // Check 1: Test results present
  const featureList = JSON.parse(
    fs.readFileSync(`coordination/feature-lists/${taskId}-features.json`, 'utf8')
  );
  const feature = featureList.features.find(f => f.feature_id === featureId);

  if (!feature.test_results || feature.test_results.exit_code !== 0) {
    violations.push({
      rule_id: 'test-required',
      message: `Feature ${featureId} missing passing test results`
    });
  }

  // Check 2: Progress file exists
  const progressFile = `coordination/workers/${workerId}/progress/current-session.txt`;
  if (!fs.existsSync(progressFile)) {
    violations.push({
      rule_id: 'progress-file-required',
      message: `Worker ${workerId} missing progress file`
    });
  }

  // Check 3: Git commits present
  try {
    const commits = execSync(`git log --oneline --since="10 minutes ago" --author="cortex"`, {
      encoding: 'utf8'
    });
    if (!commits.trim()) {
      violations.push({
        rule_id: 'git-commit-required',
        message: `Worker ${workerId} has no recent commits`
      });
    }
  } catch (error) {
    violations.push({
      rule_id: 'git-commit-required',
      message: `Unable to verify git commits: ${error.message}`
    });
  }

  return {
    valid: violations.length === 0,
    violations
  };
}

module.exports = { validateWorkerCompletion };
```

This addresses **task completion accuracy**.

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Feature decomposition too granular | Token waste on planning | Set target range 50-200 features, adjust based on task |
| Init scripts fail in worker environments | Worker spawn failures | Add fallback to old spawn behavior if init fails |
| Test commands vary by project type | Validation failures | Support multiple test frameworks (npm test, pytest, etc.) |
| Progress files grow too large | Disk usage | Archive old sessions after 30 days |
| Initializer becomes bottleneck | Slower task starts | Cache decomposition patterns, reuse similar task plans |

## Open Questions

1. **Feature count target:** 200 seems high for small tasks. Should we scale based on estimated task size?
   - Proposed: 50-100 for small, 100-200 for medium, 200+ for large

2. **Test framework support:** How to handle projects without test suites?
   - Proposed: Initializer generates test scaffolding if none exists

3. **Dependency resolution:** How to handle feature dependencies (auth-002 depends on auth-001)?
   - Proposed: Add "dependencies" array to feature schema, masters check before spawning

4. **Multiple workers per task:** Can multiple workers implement different features in parallel?
   - Proposed: Yes, but need locking mechanism on feature list updates

5. **Progress file format:** Human-readable text vs. JSON?
   - Proposed: Both - .txt for humans, .json for machines
